# Pacer 上下文与恢复：案例依据

本记录固定 Pacer 的上下文、记忆和恢复设计依据。参考仓库仅在系统临时目录浅克隆，不进入产品源码。

## Aider

- 仓库：`Aider-AI/aider`
- Commit：`5dc9490bb35f9729ef2c95d00a19ccd30c26339c`
- 参考：`aider/history.py`、`aider/coders/chat_chunks.py`、`tests/basic/test_history.py`
- 已验证机制：按 token 预算保留最近尾部；在 assistant 边界切分；递归摘要较早头部；摘要模型失败时尝试后备模型；静态仓库内容分块并利用 provider cache。
- Pacer 取舍：本地记忆使用 compact、相关性筛选和响应预算；不把完整历史反复注入模型。后续若需要 Pacer 自有摘要，必须保留最新任务、验收证据和未完成项，且摘要失败不能覆盖原始记录。

## Goose

- 仓库：`block/goose`
- Commit：`7e95db9c0cf16205118378c067c6346f6ea0d7d5`
- 参考：`crates/goose/tests/compaction.rs`、`crates/goose/src/session/session_manager.rs`、`crates/goose/src/prompts/compaction.md`
- 已验证机制：当前上下文 usage 与累计 usage ledger 分离；压缩替换 conversation 后 ledger 仍保留；provider 返回 context-length error 后压缩并重试；压缩产生明确的 history-replaced 事件；父子 session usage 可归集但不串号。
- Pacer 采用：Codex rollout 的 `last_token_usage` 作为当前窗口，`total_token_usage` 作为累计账本。压缩压力只按当前输入与阈值计算。累计 token 不再用于判断是否应该压缩。
- Pacer 暂不采用：自行调用另一个模型重写正在运行的 Codex 对话。Codex 已有原生 compaction，Pacer 只观测、记录和在真实 context-limit 失败时提供恢复证据，避免双重上下文引擎。

## OpenHands

- 仓库：`All-Hands-AI/OpenHands`
- Commit：`3949e1cc17d9443f1f4ef7d34d428baf065cd919`
- 参考入口：`openhands/app_server/event/event_store.py` 及会话事件持久化结构。
- Pacer 采用：每个 launch 独立上下文文件，最新 active 仅作为指针；旧窗口完成不能覆盖新窗口；验收、遥测和 outcome 必须绑定 launch ID。

## 必须保持的不变量

1. `current_context_usage` 与累计 `usage` 不能混用。
2. 只有当前上下文达到阈值或 provider 明确报告 context-length error，才认为需要压缩恢复。
3. 压缩或摘要不能删除累计额度、验收批次和失败证据。
4. 新摘要必须可追溯到原始本地记录；失败时保留旧记录。
5. 并发 launch 的项目根、baseline、token、验收和 outcome 必须隔离。
6. 本地文件摘要必须限制在项目根内，拒绝绝对路径和路径逃逸，并设置单文件及总大小上限。
