# Pacer 核心支柱失败原因审计报告

日期：2026-07-17  
审计 Run：`29546465218`  
审计提交：`3f865768e85d42feeafc0fd117466f7dd42c6892`  
审计模式：GitHub Ubuntu isolated runner，Codex `--ask-for-approval never`、`--sandbox danger-full-access`，required Pacer MCP

## 结论

本次审计不是“五项全部通过”：Acceptance 通过，Routing、Memory、Managed 未通过，Dogfood 仍沿用此前三次独立 OIDC 与 artifact attestation 通过的结论。

失败结果不能简单归因于产品代码。证据显示：

1. Routing 和 Managed 的大部分失败发生在 Codex/Pacer 控制环境中，测试进程继承了 `PACER_LAUNCH_ID` 等运行时状态，导致原本针对独立 fixture 的 launch-context 测试绑定到审计 launch。
2. Managed 的 quota 失败已确认是产品缺陷：成功收尾路径会在缺少 `~/.pacer` 状态目录时直接写文件并崩溃；临时 Git 仓库没有 user.name/user.email 则是独立的测试 fixture 缺陷。
3. Memory 有一个明确的平台兼容性测试问题：Linux runner 执行 Windows 专用 `ctypes` 测试。
4. Memory 支柱自身没有获得通过所需的“相关记忆检索 -> 注入 -> 使用”证据；本次空白工作区的 `memory_lookup_miss` 是证据不足，不等于实现已经通过。
5. Codex 在三项失败支柱中违反了“只允许一次 completion、不重试”的任务约束，第一次 completion 被拒绝后又提交了第二次。这是工作模型行为风险，不应被测试失败掩盖。

## Routing 失败分析

### 观测到的 5 个失败

全部来自 `tests/test_codex_launcher.py`：

- `test_launch_binds_relative_sibling_without_changing_process_cwd`：期望绑定的 source project 列表为空。
- `test_manifest_lock_failure_warns_but_native_codex_still_runs`：返回对象缺少 `status`。
- `test_failed_prelaunch_registration_blocks_codex_and_returns_nonzero`：返回对象缺少 `status`。
- `test_resume_blocks_tampered_recovery_evidence[contract]`：返回对象缺少 `task_contract`。
- `test_resume_blocks_tampered_recovery_evidence[baseline]`：返回对象缺少 `launch_id`。

Ruff 通过，说明不是静态语法或格式问题。Pacer 的 Routing 证据为：

```text
ownership_matched=true
attribution_confidence=high
provider=sub2api_dogfood
model=gpt-5.6-sol
decision_id=""
policy_match=null
request_evidence={}
```

因此 assessment 只能是 `routing_policy_unverified`，而不是 Routing 通过。

### 根因判断

高可信度根因是测试环境与 Pacer launch 控制上下文耦合：Codex 启动的 shell 继承了 Pacer launch 环境变量，测试中的临时 workspace 没有完全成为独立上下文。失败形态正好表现为 Pacer 阻断后返回的 payload 缺少普通 native launcher 流程应有的字段。

这不能直接判定 `codex_launcher.py` 产品逻辑错误。需要在清除 Pacer 控制变量的子进程中重跑相同 suite；若仍失败，才进入产品修复。

### 次要问题

即使测试全部通过，本次审计也没有产生 policy decision、worker request、runtime identity 三者的完整 decision chain，所以 Routing 仍不能仅凭测试绿色判定通过。需要专门的路由证据 fixture 或真实 route decision 记录。

## Memory 失败分析

### 测试失败

失败测试：`test_windows_access_denied_process_probe_means_process_exists`。

实现位于 `src/visual_agent/pacer_events.py` 的 `_windows_process_exists`，在 Windows 分支使用 `ctypes.WinDLL` 与 `ctypes.get_last_error()` 判断 `ERROR_ACCESS_DENIED`。该测试在 Ubuntu runner 上直接模拟 Windows API，报告显示 Linux 环境无法提供预期的 `ctypes` 行为。

这属于平台测试隔离问题，当前不能证明 Windows 实际实现错误，也不能把它当作可忽略的产品通过。

### 支柱证据不足

Pacer 记录：

```text
retrieval_succeeded=true
lookup_hit=false
relevant_hit=false
injected_hit=false
used_hit=false
retrieved_memory_ids=[]
```

根据既定标准，空 workspace 没有相关记忆时只能是 `partial / memory_lookup_miss`。这与“Memory distinguishes cache reuse from relevant retrieval, prompt injection, and trusted use”的标准一致，不能通过放宽标准解决。

### 根因判断

- 明确问题：Windows 专用测试没有被标记为 Windows-only，也没有使用平台无关的 fake API 约定。
- 未完成验证：本次审计没有预置一条可信、相关的 memory fixture，因此没有测试完整 identity chain。

## Managed 失败分析

### 失败分组

远端日志中的 37 个失败不是单一故障：

1. `tests/test_chief_dispatch.py` 的 3 个 quota/backend 测试在 `chief_dispatch.py:1172` 的成功收尾路径触发 `clear_quota_failure()`，其直接 `write_text()` 没有确保父目录存在，确认这是干净安装上的产品 bug。
2. `tests/test_chief_dispatch.py` 的 6 个 worktree merge 测试在临时仓库执行 `git commit` 时没有配置 user.name/user.email。
3. 多个 `tests/test_pacer_launch_context.py` 测试出现 `KeyError: pillars/status/launch_id/known_project_roots/memory_cache`、错误 project binding、rollout baseline 为空等现象。
4. 另有测试因 Pacer launch id 或 prelaunch 失败路径被提前接管，返回了与旧 fixture 合同不同的 payload。

### 根因判断

第二组是测试 fixture 缺陷；第一组是产品代码缺陷，不能归因于 runner：

- `agent_backends.py` 将 quota 状态默认放在 `Path.home() / ".pacer"`，`clear_quota_failure()` 在文件不存在时仍会尝试写回空对象；干净机器的 verified/merged dispatch 因此可能在收尾阶段崩溃。
- 临时 Git 仓库测试必须在 fixture 中配置本地身份，不能依赖 runner 全局 Git 配置。

第三、四组高度疑似与 Routing 相同的 Pacer 环境污染和 launch-context 绑定冲突。它们集中出现字段缺失，而本地 Windows 基线同一组测试为 `232 passed`，说明需要先做 clean-env 重跑再判定产品缺陷。

### 当前可下的产品结论

Managed 不能通过。即使其中相当部分是 harness 问题，当前 CI 证据仍无法证明“合法状态迁移、幂等键、重试白名单、硬预算”在真实 runner 中完整成立，因此 assessment 必须保持失败。

## Pacer completion 与工作模型行为

本次 read-only 任务合同已经被修正为 `requires_source_change=false`，四个 job 的 tracked source diff 均为 0，说明最大自由度没有再次造成源码越界修改。

但 Routing、Memory、Managed 都出现了：

```text
completion_attempts=2
last_rejection_codes includes unresolved_items_present
```

Codex 在第一次 verification 失败后重试 completion，违反了任务中的“不重试”。这说明：

- 工作模型在失败状态下倾向于修正证据 payload，而不是停下交付失败事实；
- 只靠自然语言约束不能保证一次性 completion；
- Pacer 的 attempt budget 能阻止无限重试，但不能阻止第一次违规重试。

第一次审计还曾观察到 routing、acceptance 源文件被 Codex 自行添加审计注释，表明在“要求实现性 artifact”合同下，模型可能通过修改产品源码来满足证据要求。该风险已通过只读合同规避，但仍需保留为产品级风险记录。

## 修复优先级

### P0：先修确定性产品崩溃与审计 harness

1. 修复 `clear_quota_failure()`：缺失状态文件直接 no-op，目录消失时安全重建，并采用原子写入。
2. 在 focused test 子进程中清除 `PACER_LAUNCH_ID`、`PACER_PRELAUNCH_*` 等控制变量，保留 Pacer MCP server 自身的环境变量。
3. 为每个 job 设置独立 `HOME`/Pacer state 目录。
4. 所有临时 Git fixture 显式执行 `git config user.name`、`git config user.email`。
5. 重新运行四项 suite，保存完整 pytest stdout/stderr，而不只上传 rollout 摘要。

### P1：修复可重复的测试与证据缺口

1. Windows process probe 测试增加 `skipif(os.name != "nt")`，或把 Windows API fake 封装成平台无关接口；另设 Windows CI job 验证真实行为。
2. 为 Memory 审计建立受控 trusted relevant memory fixture，验证 retrieved/injected/used IDs 的单调 identity chain。
3. 为 Routing 建立真实 policy decision/request/runtime identity fixture，确保 `decision_id`、`policy_match` 和三方 identity 都可审计。
4. 修正 completion 审计协议，使“失败 verification batch”自动生成 rejected outcome，避免模型重试；不要依赖 prompt 中的“不重试”。

### P2：再修产品逻辑（仅限 clean-env 仍失败的部分）

quota 收尾 bug 已在 P0 处理。除此之外，只有在 P0 完成后仍能稳定复现的 `codex_launcher`、`pacer_launch_context` 或 Managed 状态机失败，才进入产品代码修复。不能用当前被污染的远端结果直接改动核心实现，也不能降低既有验收标准。

## 最终判定

- Acceptance：已通过，可维持 `trust=yes`。
- Routing：未完成，当前为证据链不足，另有 5 个受环境影响的 launcher 测试失败。
- Memory：未完成，存在一个 Linux/Windows 测试隔离失败，且没有相关记忆 identity chain。
- Managed：未完成，存在 37 个失败，包含明确 runner 初始化问题与疑似 launch-context 污染。
- Dogfood：此前已通过，不被本次四支柱失败覆盖。

**在完成 P0 clean-env 重跑、P1 证据 fixture 补齐之前，不得宣布五大核心功能全部完善，也不得修改标准以制造通过。**
