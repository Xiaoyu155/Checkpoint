# 执行层差距修复计划（2026-07）

> 目标一句话：让 Pacer 派出去的 Codex worker 达到用户"直接开 Codex 交互式开发"的同等效果，
> 同时保住 Pacer 的真护城河 —— 独立验证、工程记忆、多赛道治理。

- 状态：实现与 direct-Codex harness 已落地；B1 direct 已做 6 次 append-only 尝试，但尚无 accepted PASS；P0 五任务完整基线、P4 真实 A/B 与默认模式决策待执行
- 前置：本计划基于 2026-07-10 对 `chief_dispatch.py` 执行链路的诊断
- 关联：`docs/Pacer开发总计划.md`、`docs/成熟度开发计划`（真实链路验证主线）

## 一、问题诊断（为什么 Pacer 派工效果远不如直接用 Codex）

用户与 Pacer 用的是**同一个 Codex 订阅、同一个模型**，差距全部来自中间层的"减法"：

| # | 差距 | 代码证据 | 严重度 |
|---|------|---------|--------|
| D1 | **无状态一次性调用**：每次派工是全新 `codex exec`，修复轮（auto_repair_once）另起新进程，首轮建立的代码理解全部丢弃 | `chief_dispatch.py:1355`、`:624-675`、`:1338`（注释明言 "Every attempt is a fresh model session"） | 致命 |
| D2 | **禁止探索省额度**：worker prompt 明令 "do not scan or grep the whole repository"，目标文件硬上限 12 个 | `chief_dispatch.py:1450-1451`、`:1438` | 致命 |
| D3 | **推理强度未对齐**：不传 `--model` 也不传 reasoning effort；用户交互式若开最大推理，headless worker 跑的是默认档 | `agent_profiles/codex.yaml:19-25`、`chief_dispatch.py:1359-1364` | 高 |
| D4 | **失败反馈有损压缩**：验证失败 → `repair_brief` 摘要 → 合成 `repair_prompt` → 喂给失忆的新进程；直接开发时模型看到的是原始报错 | `repair.py:488`（build_repair_prompt）、`chief_dispatch.py:625-627` | 高 |
| D5 | **编排层与模型内生能力竞争**：任务分解、失败降级、修复判定全是 Python 启发式；Codex 新版自动任务委托 + 最大推理已把这层吸收进模型且带上下文继承 | `chief_dispatch.py:541-596`（quota failover）、`build_worker_prompt` 整体 | 中（战略性） |

**战略判断**：执行编排正在被模型商品化。Pacer 不可替代的是模型做不到的三件事：
1. 独立验证与证据链（codex-check、verified/merge 门禁）——模型自报 done 永远不可信；
2. 跨会话工程记忆与 mission 管理；
3. 多 agent / 多 worktree 舰队治理与合并仲裁。

修复方向 = **执行层给模型松绑，治理层继续收紧**。

## 二、目标与非目标

### 目标（可量化验收）
- G1：同一基准任务集上，Pacer 派工的一次通过率（首轮 verification pass）达到直接 `codex` 交互式开发的 ≥ 90%。
- G2：修复轮不再丢上下文：repair 复用首轮会话（session resume），或至少携带原始失败证据全文。
- G3：headless worker 的 model + reasoning effort 与用户交互式配置**逐字段一致**，并写入 dispatch 记录可审计。
- G4：所有改动不削弱现有安全门禁（worktree 隔离、codex-check --strict、toolchain 违规扣留 verified）。

### 非目标
- 不做 UI/Dashboard 改版（另行安排）。
- 不改 MiMo/bugteam 低成本降级链路的语义（只保证兼容）。
- 不追求把 Pacer 变成通用编排框架；只服务"总工程师"定位。

### P0 事实基线探测（不写产品代码，产出探测报告）

**为什么先做**：后续改动依赖 codex CLI 的真实能力（版本档案停在 0.142.4 / 2026-07-02 验证），不能凭记忆写死 flag。

**任务**
1. 探测本机 codex CLI 版本与能力矩阵，逐项实测并记录：
   - `codex exec resume <SESSION_ID>` / `codex exec resume --last` 是否存在、语义如何；
   - `codex exec --json`（或等价 JSONL 事件流）是否输出 session/thread id、token 用量；
   - `-c model_reasoning_effort=<low|medium|high|...>` 配置覆盖是否被 `codex exec` 接受；
   - `--model` 在订阅账号下的行为（档案称会被拒，需复测是否仍然如此）；
   - 自动任务委托在 headless `exec` 模式下是否生效、是否有开关。
2. 取一次真实 dispatch 日志，确认 worker 实际运行的 model / effort / sandbox，与用户 `$CODEX_HOME/config.toml` 交互式配置逐项对比。
3. 建立**基准任务集**（见第四节），用直接 `codex` 交互式跑一遍，记录基线成绩（成功率、轮次、耗时、token）。

**产出**
- `docs/probes/codex_cli_capability_2026-07.md`：能力矩阵 + 每项的实测命令与输出摘录；
- `agent_profiles/codex.yaml` 更新 `verified_on` 与新增能力字段（`resume_headless`、`json_output`、`reasoning_config`）；
- 基准成绩表（写入探测报告）。

**AC**
- [ ] 能力矩阵每一项都有实测命令与原始输出为证，无"据文档说"；
- [ ] 基准任务集 ≥ 5 个任务，每个都有直接 codex 的基线成绩。

**回滚**：无（只读探测）。

### P2 解除探索禁令 + 上下文包升级（消除 D2，弱化 D5）

**原则**：**约束从 prompt 移到门禁**。prompt 不再替模型省钱、替模型划探索边界；越界行为由 codex-check / 合并仲裁在事后拦截（这套门禁已存在且有效）。

**改动清单**
1. `chief_dispatch.py :: build_worker_prompt`（:1404-1475）重写：
   - **删除** "Work efficiently to conserve model budget... do not scan or grep the whole repository"（:1450-1451）；替换为："Explore the codebase as much as needed to be confident in your change."
   - **目标文件清单降级为提示**：保留 scoped files 列表（信息有价值），删除 "Touch only the files this task requires" 的强制措辞，改为 "Likely-relevant files (verified at dispatch time)"；12 个上限放宽到 30 或按 token 预算截断；
   - **保留**的硬约束仅限安全边界：不编辑 Checkpoint plan 记录、不动 archive/graveyard、Dart toolchain 禁令（这些有真实事故背景，保留并注明会被门禁扣留）；
   - 验证命令段保留（"Before claiming done, run ..."），并追加一句：允许在过程中多次运行验证，而非只在最后。
2. repo map（:1340-1346）保留，但明确其定位是加速起步而非划界。
3. **护栏对等加强**（因为 prompt 松绑了）：
   - 确认 `workbench_audit.py` / 合并仲裁对"改动越界"（触碰非白名单目录）有检测；若只靠 prompt 约束，本阶段补一条 dispatch 后审计：diff 触碰 `_is_non_product_path` 目录 → verification 直接 fail 并写明原因。

**测试**
- `tests/test_chief_dispatch.py`：prompt 不再含禁探索文案的断言（防回归）；越界 diff 触发审计 fail 的用例。

**AC**
- [ ] 基准任务集上首轮通过率相对 P0 基线提升（预期这是单项收益最大的阶段）；
- [x] 越界改动被门禁拦截的用例通过（松绑不等于失守）；
- [ ] 额度消耗记录进 dispatch ledger（见 P5），涨幅可见可评估，但**不以省额度为由回退本项**——额度问题由订阅额度感知（statusline 方案）单独治理。

**回滚**：`prompt_style=legacy` 仅恢复旧的 12 文件提示上限，不恢复禁探索文案；安全边界始终由门禁执行。

### P3 会话续接修复轮 + 原始证据回灌（消除 D1、D4）

**入口条件**：P0 探明 resume 与 session id 捕获方式。分两条路，P0 结果决定走哪条：

**路线 A（首选）：headless resume 可用**
1. `run_process_capture` / `_run_worker_attempt`：从 `codex exec` 输出（JSONL 事件或 banner）解析并持久化 `session_id` 到 worker record（对齐 claude-code 已有的 ledger 模式，`chief_dispatch.py:2611-2620`）。
2. `build_worker_command` 新增 `resume_session_id` 参数：有值时 argv 变为 `codex exec resume <id>`，prompt 只含增量指令。
3. auto_repair_once（:624-675）：优先带首轮 `session_id` resume；session 丢失/过期时回退路线 B。
4. repair prompt 内容改造（`repair.py :: build_repair_prompt`）：resume 场景下不再重复 objective 全文（会话里已有），只给：验证 verdict、失败的具体命令、**原始失败输出**（见下），以及"修完再跑验证命令"。

**路线 B（兜底）：resume 不可用**
1. 保持新进程，但 repair prompt 携带**原始失败证据全文**：失败测试/命令的 stdout+stderr 原文，尾部截断至 32KB（经 stdin 传入，:1369-1371 已解决 argv 长度问题）；`repair_brief` 摘要保留作为导读，不再是唯一信息源。
2. 携带首轮 worker 的行为摘要：读过/改过的文件清单（从 diff 与日志提取），减少重复探索。

**公共改动**
- 修复轮次上限从 1 提到可配置（默认 2）：resume 模式下每轮边际成本低，一次修复上限是旧架构（每轮全价）的遗留假设；
- 每轮修复后都跑完整 `run_dispatch_verification`（现有行为保持），轮次与 verdict 全部入 `verification_attempts`。

**测试**
- `tests/test_chief_dispatch.py`：session_id 解析（给定伪造 JSONL/banner 样本）；resume argv 构造；resume 失败回退路线 B；原始证据截断逻辑；多轮修复的轮次上限。
- 用 fake runner（现有 `command_runner`/`codex_runner` 注入点）覆盖，不依赖真实 codex。

**AC**
- [ ] 真实任务上观察到：修复轮不再重新读一遍首轮已读的文件（对比两轮日志的文件访问）；
- [ ] 基准任务集"失败→修复→通过"链路的总耗时与 token 较 P0 基线下降；
- [x] resume 不可用错误（含老 CLI `unrecognized subcommand 'resume'`）由 fake runner 回归证明会自动走路线 B，无崩溃；真实老版本抽测仍待基准环境。

**回滚**：`repair_strategy=fresh|resume` 配置项，`fresh` 即旧行为。

### P4 委托模式：整体目标单会话（消除 D5）

**思路**：既然 Codex 已内置任务委托，Pacer 不再预先把 objective 拆成细粒度 track 指令，而是提供一种新派工模式：**整个 objective + 丰富上下文交给一个会话，让模型自己决定拆分与委托；Pacer 只在外面做验证、审计、合并仲裁。**

**改动清单**
1. `chief_dispatch.py` 新增 dispatch 模式 `mode=delegated`（默认仍是现有 `tracked`）：
   - prompt = objective 全文 + acceptance criteria + repo map + 验证命令 + 安全边界，**没有** scoped files、没有分解好的步骤；
   - 单 worktree、单会话、允许长 timeout（可配置，默认上限翻倍）；
   - 验证、审计、门禁与 tracked 模式完全共用。
2. `cli_chief.py` / Dashboard：暴露模式选择。
3. **A/B 评测**：基准任务集每个任务分别用 `tracked`（P1-P3 改造后）与 `delegated` 跑，记录成绩入 ledger。

**AC**
- [ ] delegated 模式端到端跑通基准任务集，门禁行为与 tracked 一致；
- [ ] 产出 A/B 对比报告，据此决定默认模式（决策写入本文档附录）。

**回滚**：新模式独立开关，不影响 tracked 链路。

## 四、基准任务集（P0 建立，全程复用）

选取原则：真实、可自动验证、覆盖不同难度与形态。建议构成：
