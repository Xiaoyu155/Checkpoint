## 一、额度问题：已解决，不是待办

**结论先行：额度问题这一页已经翻过去了，不需要等、也不需要再做任何事。**

解法是一行配置，已经写进 `~/.claude/settings.json` 并验证生效：

```json
{
  "model": "opus",
  "effortLevel": "medium",
  "autoCompactWindow": 100000,
  "skipDangerousModePermissionPrompt": true
}
```

`autoCompactWindow` 是 Claude Code 配置 schema 里的正式项（`int, min 1e5, max 1e6`），等价物还有 CLI 参数 `--autocompact` 和环境变量 `CLAUDE_CODE_AUTO_COMPACT_WINDOW`。作用是**在会话内**把上下文压在 10 万 token 以内：不杀进程、不丢 `/model`、不丢 MCP、摘要由引擎自己做。

### 为什么这一行就够了

实测归因（ccusage 跑本地 JSONL，8/5 起 56 个会话 / 53.4 亿 token）：

| 事实 | 数字 |
|---|---|
| 消耗集中度 | 前 12 个会话 = 96%，最大单个 7.17 亿 |
| 小会话总和 | 40 个 10M 以下的会话加起来 = 1.3% |
| 有效载荷率 | 0.1–0.2%，即约 800:1 的历史重读 |
| 高上下文占比 | 93% 的消耗发生在 >150k 上下文 |
| Pacer 派工会话 | 每个约 1MB，全部不显著 |

所有"怪兽会话"都是人在 `D:\Projects` 里的交互式开发。**额度问题跟 Pacer 的派工机器一点关系都没有**，是单会话上下文太长导致的重复计费。把上限从 150k+ 压到 100k，就是 1.5–2 倍的节省，零风险。

### 为什么放弃了杀进程轮转

中途做过一套"到阈值杀掉会话、带蒸馏交接件重启"的方案（`claude_rotation.py`）。放弃作默认，原因是：

- 中断正在做的事；
- 丢会话内存态——实测第一个丢的就是 `/model` 选择（已修，但这是信号）；
- 新会话要把已经"认识"的文件重读一遍，这笔重新摸索的成本抵消了上下文归零的收益。

现改为默认关闭的激进档，要用得显式 `PACER_CLAUDE_ROTATE=1`。

### Pacer 在这件事上的位置

`pacer claude` 交互式启动时会自动注入 `--autocompact 100000`（`PACER_AUTOCOMPACT=off` 关闭；你显式给过 `--autocompact` 时不覆盖）。

但说实话：**这个注入是可有可无的**，因为 settings.json 那一行是持久的，不经过 Pacer 也一样生效。省额度这件事上 Pacer 的贡献已经归零。

启动命令不变：`pacer claude --permission-mode bypassPermissions`。

## 三、遗留风险与代价

1. **证据侧测试覆盖被削弱。** 那些模块的测试测的是 `chief_dispatch` 里的调用点（`_run_dispatch_delivery_check` 之类），随托管一起删了。在它们上面建 `pacer verify` 时**必须重新补测试**，不能假定它们还被守着。
2. **`cloud_api/` 被删，需要确认。** 仓库根目录有个未跟踪的 `支付需要材料.txt`。如果那件事跟这个微信支付网关有关，`git revert cf2c76b -- cloud_api` 或从 `c55be9c` 取回即可。
3. **分支未合并、未推远程。** 三个仓库都没有远程地址这个老问题仍在（见 `阶段性报告_2026-08-06.md`）。
4. **`pacer.exe` 重装时会报文件占用**——因为当前会话本身就是 `pacer claude` 起的。入口点没变，现有 exe 照常工作；换个窗口 `pip install -e .` 即可。
5. **docs/ 目录没动。** 里面很多文档描述的是已删除的功能，读的时候注意时间戳。

## 四、下一步：三个候选，已排序

标准是两条：**引擎自己会不会长出来**，以及**用户实际用不用得上**。

### 推荐先做：防目标漂移（重锚）

`autoCompactWindow: 100000` 上线后压缩会更频繁地触发。压缩保留的是"最近在干什么"，**不保证保留"你最初要什么"**。长会话里目标被摘要磨掉是结构性的。

仓库里搜不到任何 `reanchor` / `anchor_goal` 实现——2026-08-05 定的 P0 从没落地过，`feat/pacer-client-role` 分支就停在这儿。

形态最轻：一个 Claude Code hook，每 N 轮或每次 compact 之后把原始目标原文贴回上下文，并追问"现在这步跟它什么关系"。落地量小、验证快、不好用当天就能删。

### 其次：验收器 `pacer verify`

引擎结构上做不到的唯一一件事：**它不核自己的账**。`acceptance_discrimination.py` 已实现 base 差分探测三档结论——`verified`（改前红、改后绿）/ `regression_clear`（本来就绿，只证明没搞坏）/ `unverified`（门自己坏了或没证据）。2026-08-05 跟 GitHub 九个同类项目对撞，八个落后，**唯一空白就是这个交付关卡**。

形态：`pacer verify` 命令，或挂成 Claude Code 的 Stop hook。工作量比重锚大一档，适合重锚验证成功之后接着做。

### 再次：跨引擎接力

Claude 额度撞墙时打包交接件转 Codex 继续干。这是唯一"引擎越强也不会自己长出来"的能力——因为它跨厂商，Claude 不会帮你切到竞品。门槛在交接件质量：接不上就是重新摸索。

### 不推荐现在动的

- **产品化 / 人话呈现**（`pacer_voice.py`）：对会看代码的人无用，对不看 diff 的人是刚需。但这是创业方向，第一步是去找人聊，不是写代码。
- **省额度、跨会话记忆、派工、无人值守托管**：已被引擎吃掉或已被实测否掉，不要再投人力。

## 五、复盘

这一阶段最有价值的产出不是代码，是两个被证据钉死的判断：

1. **额度问题的解不在 harness，在引擎自带的旋钮里。** 花力气建的轮转代理，最后输给了一行配置。
2. **"agent 每强一次，harness 就该薄一层"** 又一次被印证——这次是自己动手砍掉了 75%。

Pacer 该活的地方越来越窄，但也越来越清楚：**不是替 agent 干活，是替你核 agent 交的活。**
