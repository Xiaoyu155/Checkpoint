# Pacer 验收闸门

Pacer 把验收拆成三类证据：AST 规则检查代码形态，受限子进程检查可执行行为，GPU 差分检查适合批量数值比较的路径。它们回答的问题不同，不能互相替代；GPU 检查只适用于有明确参考实现和可比较输出的任务。

```mermaid
flowchart LR
    PATCH[模型生成的补丁] --> AST[AST 规则检查]
    AST -->|通过| RUN[受限反例与项目验收命令]
    RUN -->|数值路径适用时| DIFF[GPU 差分批测]
    RUN -->|其他路径| RESULT[汇总验收证据]
    DIFF --> RESULT
```

图表示验收职责，不保证每个任务都会按同一顺序经过所有闸门。AST 和项目验收由本机执行；GPU 差分只应在任务提供可复现的输入生成规则、参考实现和比较标准时启用。

## 1. AST 规则

`anti_slop.py` 对改动的 Python 文件解析 AST，检查常见的空洞实现或假通过模式，例如恒真断言、没有有效断言的空测试、吞掉异常的空处理，以及用 `pass`、`return True` 等替代实际实现。发现阻断项时，编排器会拒绝当前候选并要求修复。`witness_verifier.py` 还会检查测试断言是否有实质内容。

AST 闸门适合快速发现结构明确的低质量改动，不需要运行目标代码。它不能证明功能正确，不能发现所有逻辑错误，也不是通用安全分析器；目前这些规则主要覆盖 Python。

## 2. 受限子进程与项目验收

独立审查路径可要求审查器给出 1 到 3 条可执行断言。`task_review.py` 会先按 AST 白名单限制断言语法和可调用对象，再启动独立 Python 子进程执行。子进程使用临时工作目录、隔离 Python 启动选项、有限的环境变量和执行超时；异常或断言失败会作为失败证据返回。它用于验证具体行为反例，不代表完整的项目测试运行。

项目验收命令由 `command_verification.py` 按 argv 列表和安全策略启动，并设置超时、记录输出、检查验收输入是否被改动。该命令在仓库工作目录中运行，继承当前进程环境；它不是容器或操作系统级沙箱。

受限反例子进程同样不是 OS 安全边界。它会导入并执行目标模块，使用当前用户的系统权限；代码仍可能访问本机文件或尝试其他副作用。AST 白名单约束的是审查断言，不会把被测模块变成可信代码。因此，不要把不可信仓库或恶意目标代码交给这条执行路径。不要把“进程隔离、超时”理解为网络、文件系统或系统调用都已被隔离。

## 3. GPU 差分

差分测试把同一批输入交给参考实现和候选实现，再比较结果或检查共同的不变量。GPU 的工作是并行评估大量输入或数值情景，快速找出不一致；参考实现、比较规则和不变量才定义了正确性。发生差异时应保留随机种子、最小失败输入、双方输出和比较指标，以便在 CPU 上重放。

GPU 差分特别适合确定、可批处理的数值代码，例如向量化变换、数值评分、模拟和大量参数组合。应由 CPU 独立重放抽样或失败样例，避免把 GPU 输出本身当作正确性证明。浮点结果要按领域设定容差；状态码、形状和离散决策通常应精确相等。

当前仓库没有通用的 `diff_spec` 解析器或代码补丁模糊测试命令。`vnext/strategy_search.py` 提供的是可选 PyTorch CPU/CUDA 策略评分，并用 Python CPU 路径复算候选、检查 holdout；这证明了一个数值切片的 GPU 评分和 CPU 复算链路，不等于已经能对任意代码补丁执行 GPU 差分模糊测试，也没有接入常规补丁验收流程。

## `diff_spec` 写法

仓库目前没有被程序读取的 `diff_spec` schema。下面是编写和评审差分任务时可采用的 YAML 约定示例，不是现有 CLI 配置；实际接入前仍需实现解析、字段校验、执行和结果记录。路径和函数名应替换为项目内真实的参考实现、候选实现和输入生成器。

```yaml
version: 1
target:
  reference: "tests.reference:normalize"
  candidate: "src.package.normalize:normalize"
inputs:
  generator: "tests.diff_inputs:make_cases"
  seed: 1729
  cases: 50000
  constraints:
    dtype: float64
    shape: "1..4096 elements"
    values: "finite values; include zero, valid boundaries, and extreme valid values"
compare:
  fields:
    - path: "values"
      mode: allclose
      rtol: 1.0e-7
      atol: 1.0e-9
    - path: "status"
      mode: exact
  invariants:
    - "output length equals input length"
execution:
  device: cuda
  batch_size: 512
  timeout_seconds: 60
report:
  max_failure_examples: 10
```

编写时要明确：

- `target` 指定稳定的参考实现和待验收候选实现；两者必须接收同样的输入。
- `inputs` 给出可复现的生成器、种子、样本数和合法输入边界。生成器应覆盖边界值，也要避免生成违反业务前置条件的无效数据，除非任务专门验证错误处理。
- `compare` 对每个结果字段指定精确比较或数值容差，并列出独立于参考实现的不变量。容差要对应业务精度，不能为了消除失败而任意放宽。
- `execution` 限定设备、批大小和时间预算；还应由实现方控制内存上限。超时、显存不足、缺少 GPU 或结果无法解析都应记作未验收，不能静默当作通过。
- `report` 限定失败样例数量，并记录种子、输入、参考值、候选值和误差，保证失败可重放。

## 显卡适用范围

| 场景 | GPU 的作用 |
| --- | --- |
| 大量同形状数值输入、参数组合或独立模拟 | 并行执行批次，增加差分覆盖量或缩短评分时间 |
| 纯函数或受控数值内核，有稳定 CPU 参考实现 | 对相同输入批量计算并定位 CPU/GPU 或版本间差异 |
| 小批量、短函数、频繁调用 | 通常帮助不大；数据搬运和启动开销可能高于计算 |
| AST 索引、补丁匹配与应用、文本处理、文件和网络 I/O、构建流程 | 主要受 CPU、磁盘或外部服务限制，GPU 无直接加速路径 |
| 并发、异步、UI、时间依赖或有副作用的功能 | GPU 差分难以隔离和复现；应使用针对该行为的测试与环境控制 |
| 缺少可信参考结果或比较规则含糊 | GPU 只能更快地产生结果，不能判定结果是否正确 |
| 本地大语言模型推理 | 不属于 Pacer 的 GPU 用途；云端模型负责生成代码，本机负责索引、补丁和验收 |

是否启用 GPU 应由数据规模、可向量化程度和端到端测量决定。只报告 GPU 内核耗时会漏掉数据生成、传输、CPU 复算和结果归并的成本；验收要关注端到端耗时与差分覆盖，而不是利用率数字。
